# Troubleshooting

> Generated by `/buddy:docs`. Issues below are derived from constraints documented in the codebase itself (comments, configs, and test suites), not hypotheticals.

## Development

### `npm run dev` fails or bindings are missing
- Node must be **>= 22.13** (`engines`). Check `node --version`.
- Miniflare reads bindings from `wrangler.jsonc` and secrets from `.dev.vars`. If `.dev.vars` is missing, copy `.dev.vars.example` and fill in `OPENAI_API_KEY`.
- The placeholder D1 `database_id` in `wrangler.jsonc` is intentional — Miniflare ignores it. Do not "fix" it locally; the deploy workflow resolves the real id by name.

### Inpainting (`/api/workbench/inpaint`) fails locally
The Workers AI binding proxies to Cloudflare's network **even in local dev**. It requires a logged-in `wrangler` session and consumes the account's free-tier neurons. Run `npx wrangler login` first; if you see auth errors, that's the cause — not the route handler.

### Generation returns 413 (payload too large)
Request bodies are capped at **32 MB** (`next.config.ts` `serverActions.bodySizeLimit`, applied by vinext to route handlers too). A single 4K PNG is ~20 MB, so one oversized reference plus overhead can exceed it. References should flow through the chunked transport (`/api/references/start|part|complete`) rather than any single request.

### Access-related 401/403 locally
`worker/access.ts` rejects requests without a valid Cloudflare Access JWT — but only when `CF_ACCESS_TEAM_DOMAIN`/`CF_ACCESS_AUD` are set. Local dev must blank them in `.dev.vars` (there is no Access proxy on localhost). If you copied production values into `.dev.vars`, remove them.

## Build & deploy

### Deploy fails at "Resolve D1 database id"
The workflow requires a D1 database named exactly `material-collager-db` on the account (`wrangler d1 list`). If it was renamed or the API token lacks D1 read permission, the step exits with "D1 database material-collager-db not found".

### Production serves but every request is rejected
Check the Access application configuration (Zero Trust → Access → Applications → material-collager). The `CF_ACCESS_AUD` in `wrangler.jsonc` must match the application's AUD tag; a recreated Access app gets a new AUD.

## State & data

### Workbench draft won't load after an update
Draft persistence is versioned and migrated — see `tests/workbench-persistence-migration.test.mjs` for the expected shapes. If a schema change breaks old drafts, the migration in `app/components/workbench/store.ts` is the place to fix it, with a new test case. Do not clear user drafts as a "fix".

### D1 tables missing on a fresh deployment
By design: tables are created lazily by the generation-history service (`db/schema.ts` comment). A fresh private deployment provisions its D1 binding on first use — no separate setup step. An empty database is not an error until a write has happened.

## Visual & motion

### Page transition shows a flash or no animation
- `TransitionLink` falls through to plain navigation when `document.startViewTransition` is missing or `prefers-reduced-motion` is set — both are intentional. Development logs every skipped/timed-out transition with a reason (`[transition] …` in the console).
- The transition waits for the destination's readiness signal (`app/lib/route-ready.ts`), capped at `READY_BUDGET_MS` (900 ms, measured). A `[transition] timeout` log means the destination never called `markRouteReady` — check the route renders `RouteReady` (or, for the Library, that `SceneWheelV2` still carries its signal).
- The `::view-transition-old(root)` rule must keep `animation: mc-hold` — `animation: none` makes the outgoing page vanish behind the wipe (documented in `app/effects.css`).

### Transition hangs, then hard-cuts after ~4 seconds
Something inside the update callback is awaiting `requestAnimationFrame`. Rendering is suspended while the callback runs, so rAF never fires there (microtasks and tasks do). Signal readiness from effects or tasks, never rAF — verified empirically in `specs/20260821-page-transitions-upgrade/research.md`.

### Dev page crashes with "does not provide an export named …" after a config change
The Vite dep graph is mixed between two optimizer states (check the `?v=` hashes in the failing imports — two different hashes on one page confirms it). Fix: stop the dev server and restart it **without** deleting `node_modules/.vite` — the settled registry makes the next start consistent. Deleting the cache makes it worse: every fresh start re-discovers deps mid-page-load and re-breaks the first load.

### Scene comparisons don't match the reference
Freeze the scene deterministically before comparing: `?qa=1&progress=0.40` etc. The mandated viewports and progress states are in `AGENTS.md`; discrepancies belong in `docs/visual-qa.md`, not in commit messages.

## Performance profiling

- Frame-rate regressions on the R3F surfaces: profile with the browser's performance panel against the four mandated viewports (1440×900 down to 390×844); `AGENTS.md` blocks completion on high-severity interaction discrepancies.
- View-transition inspection: Chrome DevTools → More tools → Animations captures view transitions and can replay them at 10% speed.

## Test suite

### Workbench tests interfere with each other
They are expected to share state: `npm run test:workbench` runs with `--test-isolation=none`. Write new workbench tests to be order-tolerant within that model, or add them to a different suite.

### TypeScript test files fail to run
Suites run via `node --experimental-strip-types --test`. That strips types only — no enums, no namespaces, no decorators in test files.
